零、先说我是什么样的人

建筑工程出身，不是科班。所以我的路子和科班不同：

  • 带着问题去学技术，不是先学理论再找用途
  • 每个东西都是为了解决一个真实麻烦，不是练手

结果是：单点深度不如专职的人（不如专职前端做设计，不如算法工程师写算法），但端到端的完整能力极稀缺。一个产品从零到上线，绝大多数人只负责其中一段。

领域 2｜后端工程

做过：2,484 个路由的 API 体系、32 张表设计、SQLite→PostgreSQL 迁移、多 worker 任务队列（SELECT FOR UPDATE SKIP LOCKED）、双登录认证（密码 + 短信）、CSRF 防护、按用户权限分流的文件服务。

四个能脱稿讲的真实故障：

  1. 进度永远 0% — 四进程各自内存字典，任务建在 #2，轮询进 #3 查不到。改落数据库，顺带解决重启丢状态。
  2. 限流失效 — 内存计数器四进程各算各的，配 100 次/分实际放行 400 次。
  3. 支付回调 302 — 回调地址多写了路径前缀，跳转丢 POST body。
  4. 时区错乱 — 两种时间基准混在一张表，同一天记录差一天。

领域 3｜AI 模型部署与显存调优

单卡 24G 跑通的：

类型 模型 实测
画图 FLUX.1 dev fp8 + IP-Adapter + ControlNet 20–40 秒/张
图生视频 Wan 2.1 / SVD 512p 短片段，第 2 秒易崩脸
口型 Sonic / LatentSync / Wav2Lip 4.8 秒音频跑 205 秒
语音合成 IndexTTS（154 音色 + 克隆）/ CosyVoice 常驻 6.7G
语音识别 whisper.cpp（CUDA 自编译） 中文优先，常驻 2.3G
文本 llama.cpp / vLLM，27B / 32B 量化下沉

核心经验：

  • 显存不够不报 OOM，而是慢十倍然后给废图（在搬权重不是算）
  • 可用显存 = 单卡 − 常驻（我机器常驻 15G，24G 卡实际只有 9G）
  • 权重 ≤ 可用显存 × 0.8 才安全
  • 双卡 ≠ 双倍显存（除非做 tensor parallel）
  • 新架构显卡需要新 CUDA，老框架直接编译失败

领域 11｜服务器运维与部署

  • Linux：无图形界面服务器全套配置
  • 服务托管：systemd（自动重启 / 日志 / 依赖顺序）
  • 反代：nginx / Caddy、子路径挂载、SSL、文件内部重定向
  • 穿透：Cloudflare Tunnel、SSH 反向隧道、Tailscale 组网
  • 容器：Docker Compose 多服务编排
  • 六层排查法：进程 → 端口 → 反代 → 日志 → 数据库 → 外部 API

案例：家宽无公网 IP 打通外网访问并配 HTTPS；云服务器 443 被封改 SSH 反向隧道；无显示器服务器装 Windows 虚拟机。

领域 12｜消息机器人与多 Bot 运维

  • 多个 Bot 实例独立 profile、systemd 托管、Docker 沙箱、掉线自恢复
  • 企业微信接入：AI Bot 长连接模式，扫码登录、凭据管理
  • 邮箱自动化：IMAP 读取、规则过滤、定时巡检
  • 定时任务体系：cron 管理、失败告警、避免重复执行

踩过的坑：进程内重启自己会自杀 → 用一次性任务脱离进程树；多实例必须开独立模式；沙箱里的技能目录是软链，删除会伤到源目录。

领域 13｜支付与商业化闭环

  • 微信支付 v3：Native 扫码、签名验证、回调验签、AES-GCM 解密
  • 积分计费：扣费规则单一真相源（数据库驱动）、步骤单价可配
  • 订单退款：实付 / 赠送分离追踪、退款上限校验
  • 充值流程：下单 → 支付 → 回调 → 到账 → 赠送，全链路幂等

三个坑：回调地址多前缀 → 302；公钥不匹配 → 401；APIv3 密钥不匹配 → AES 解密失败。

领域 14｜浏览器自动化与逆向

  • 全自动发布：技术社区平台完整发布流程（含标签注入、签名绕过）
  • CDP 接管模式：用户扫码，程序控制同一窗口，不碰密码验证码
  • 绕 WAF：识别无头指纹 → 改有头模式
  • 逆向工具链：jadx / apktool / Ghidra / radare2 / frida / mitmproxy
  • 爬虫：招标公告、企业信息、视频数据

关键经验：命令行通但浏览器 403 = 指纹问题不是 IP；JS 的 .click() 不触发框架事件委托，必须真鼠标；点不动的按钮先抓服务端错误，别瞎试界面。

四、三个版本的自我介绍

30 秒

我做 AI 应用落地和工程数字化的。一个人写过六万多行的 AI 内容生产平台，也做过建筑行业的微信小程序（45 个页面）。强项是让 AI 功能真正上线跑稳，还能把成本压下来。

2 分钟

我建筑工程出身，转行做开发，现在是独立开发者。

两块最主要的作品：一是 AI 内容生产平台，输入故事自动出成片，六万多行代码、两千多个接口、三十二张表，从第一行代码到线上运维都是我；二是建筑行业的微信小程序，45 个页面、14 个业务模块，做过跨平台全量迁移，写了完整的代码审计报告。

最难的不是调 AI 接口，是工程问题：多进程状态、支付幂等、任务队列、成本控制。我把 21 个真实故障都写成了复盘，公开在 GitHub。

我的定位是：能把 AI 从 demo 做到上线的工程人，而且懂工程行业。

10 分钟（按顺序讲）

  1. 我是谁：建筑转开发，独立开发者
  2. 代表作一：AI 内容生产平台（挑 2–3 个环节细讲）
  3. 代表作二：建筑小程序（迁移 + 审计 + 发版）
  4. 深讲一个故障：多进程下进度永远 0%
  5. 成本观：AI 视频 85% 的钱花在生成，降废片率比换供应商有效
  6. 边界：不做算法、不做设计，专注把应用做稳
  7. 反问：你们现在最卡的技术问题是什么？

五、最后

不是「我会用很多工具」——工具每年都在换。

真正稀缺的是这三样：

  1. 端到端能力 — 从想法到上线到运维，一个人走完
  2. 真实故障经验 — 21 个坑，每个都能讲出根因和解法
  3. 懂两个世界 — AI 圈里懂建筑，建筑圈里懂 AI

技术会过期，这三样不会。
